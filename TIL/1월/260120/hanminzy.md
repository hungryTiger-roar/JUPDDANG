## Git 협업의 본질과 워크플로우

### 1. Git 저장소의 이해
- **필요성:** Git 없이 협업하면 누가 어떤 작업을 했는지 추적할 수 없다.
- **저장소(Repository):** 소스코드와 모든 작업 기록(누가, 언제)이 저장되는 보관소.
  - **원격 저장소 (Remote):** 서버(클라우드)에 있는 팀 공유 공간.
  - **로컬 저장소 (Local):** 내 컴퓨터에 있는 개인 작업 공간.

---

### 2. 브랜치 (Branch) : 안전한 실험실
- **정의:** 서로를 방해하지 않고 독립적으로 작업을 수행하는 공간.
- **활용:** 실패에 대한 두려움 없이 다양한 시도 가능.
  - **성공 시:** 메인 코드에 합침 (Merge).
  - **실패 시:** 미련 없이 삭제.
- **동시 개발:** 완벽히 분리된 공간이므로 여러 기능을 병렬로 개발 가능.

---

### 3. 커밋 (Commit) : 기록의 단위
- **정의:** 누가, 언제, 무엇을 바꿨는지 Git에 기록하는 행위.
- **언제 해야 하는가?**
  - **시간이 아닌 '기능' 단위:** 논리적으로 완결된 작업 단위일 때.
  - **작게, 자주:** 변경 사항을 추적하기 쉽도록 작은 단위로 자주 커밋.

## 협업 프로세스와 규칙 (Ground Rules)

### 1. Merge Request (MR) & Code Review
- **프로세스:** 작업 완료 → MR 생성 → 코드 리뷰 → 승인(Approve) → Merge.
- **목적:** 버그 수정, 코드 품질 향상, 팀원 간 지식 공유.
- **규칙:** 최소 1명 이상의 승인을 받아야 합칠 수 있도록 설정 권장.

### 2. 충돌 (Conflict) 관리
- **마인드셋:** 충돌은 에러가 아니다. "둘 중에 어떤 코드를 쓸까?"라는 Git의 질문일 뿐이다.
- **대처:** 두려워하지 말고 팀원과 상의하여 올바른 코드를 선택하면 됨!

### 3. 팀이 반드시 지켜야 할 최소 규칙
- **직접 커밋 금지:** `main`, `develop` 브랜치에 직접 커밋 금지 (무조건 MR 활용).
- **브랜치 네이밍 준수:** `Sjh_work` (X) → `feature/기능명`, `fix/버그명` (O).
- **브랜치 즉시 삭제:** Merge가 끝난 브랜치는 혼란 방지를 위해 바로 삭제.
- **1일 1커밋 & 잦은 Merge:** 브랜치를 길게 가져가지 말고 2~3일 내에 Merge.

### 4. 커밋 컨벤션 (Conventional Commits)
팀의 효율적인 협업을 위해 일관된 메시지 형식을 유지한다.

- **Header:** `feat: 닉네임 중복 체크 기능 구현` (타입 + 설명)
- **Body:** "서비스 요구사항에 따라 DB 조회를 통해 중복 확인..." (상세 내용)
- **Footer:** `JIRA : S01P99Z111-08` (관련 이슈 트래킹)
