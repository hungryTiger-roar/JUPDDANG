## 1. 배포 안정성을 위한 환경 격리 전략

CI/CD 구축 과정에서, 로컬 호스트에서의 성공이 배포 서버에서의 성공을 보장하지 않는다는 점을 고려했다. 운영 환경의 안정성을 해치지 않으면서도, 실제 서버 환경에서 자유롭게 테스트할 수 있는 **'이중 컨테이너 구조'**를 설계했다.

### 📌 Prod와 Dev의 공존

* **컨테이너 설계:** 하나의 배포 서버 안에서 `Backend`와 `DB` 컨테이너를 **운영**용과 **개발**용으로 명확히 분리하여 구성했다.
* **의도:** 단순히 포트만 나누는 것이 아니라, 데이터 볼륨과 환경 변수까지 격리함으로써 개발 서버에서 발생한 데이터 오염이나 서버 다운이 운영 서버에 전혀 영향을 주지 않도록 설계했다.

### 📌 서버 레벨 테스트의 중요성

* **미리 보는 운영 환경:** 로컬 개발 환경과 배포 서버 환경은 미묘하게 다르다.
* **효과:** `Dev` 컨테이너를 통해 배포 서버 환경에서 기능 테스트를 선행함으로써, 실제 `Prod` 배포 시 발생할 수 있는 환경 종속적인 버그를 사전에 차단할 수 있게 되었다. 즉, **'서버 단위의 통합 테스트'**가 가능해졌다.

## 2. 실시간성을 고려한 GIS 데이터 처리

'땅따먹기'라는 게임의 특성상 사용자의 위치 변화가 즉각적으로 시각화되어야 한다. 이를 위해 공간 인덱싱 라이브러리인 **H3**의 특성과 통신 방식을 고민했다.

### 📌 H3 라이브러리의 경량성 활용

* **로직 분석:** H3를 사용해 위경도를 육각형 그리드 인덱스로 변환하는 로직 자체는 CPU 연산 비용이 크지 않음을 확인했다.
* **판단:** 서버의 연산 부하보다는, **'어떻게 데이터를 주고받느냐'**가 사용자 경험을 결정짓는 핵심 요소임을 파악했다.

### 📌 Polling vs WebSocket

* **통신 프로토콜 선정:** 단순 HTTP 요청은 오버헤드가 크고 실시간 반응성이 떨어진다.
* **결정:** **WebSocket**을 도입하여 양방향 통신 채널을 열기로 했다.
* 팀에서 설정한 주기 혹은 실시간 스트림으로 GPS 데이터를 지속적으로 수신하고, 서버는 가벼운 H3 연산 후 즉시 결과를 반환한다.


* **기대 효과:** 사용자가 이동할 때마다 앱 화면의 땅이 즉각적으로 반응하여, 끊김 없는 몰입감을 제공할 수 있다.
