## 1. 서비스 복잡도 관리: 실시간성 vs 결과 정합성

기획 단계에서 '보스 레이드'의 재미를 위해 실시간 타격과 복잡한 상태 관리(배터리 충전/방출)를 고려했으나, 이것이 사용자 경험과 개발 안정성 사이에서 불필요한 트레이드오프를 만든다는 것을 깨달았다. 과감하게 **'사후 정산(Post-processing)'** 모델로 아키텍처를 피벗했다.

### 📌 실시간 통신의 허와 실

* **문제 인식:** 이동 중인 사용자에게 실시간 소켓으로 데미지를 동기화하는 방식은 네트워크 불안정 시 '유령 타격'을 유발하고, 트랜잭션 관리의 난이도를 기하급수적으로 높인다.
* **해결책:** 복잡한 실시간 로직을 걷어내고, **Set 교집합**을 활용한 일괄 정산 방식을 택했다.
1. **플로깅 중:** Redis Set에 사용자가 방문한 H3 인덱스만 가볍게 적재.
2. **종료 시:** `[방문 경로 Set] ∩ [보스 위치]` 교집합 연산 한 번으로 타격 여부를 판정.


* **효과:** 프론트엔드는 단순히 위치만 전송하면 되고, 백엔드는 트랜잭션 하나(`@Transactional`)로 데이터 정합성을 완벽하게 보장할 수 있게 되었다.

## 2. DB 설계의 정석: 스냅샷과 로그의 분리

"보스별로 테이블을 나눠야 하나?"라는 고민에서 출발하여, 데이터의 성격에 따라 **'현재 상태'**와 **'과거 기록'**을 분리하는 정석적인 설계를 도출했다.

### 📌 Anti-Pattern 회피와 정규화

* **문제:** 보스가 추가될 때마다 테이블을 생성하는 것은 유지보수 불가능한 구조다. 또한, 하나의 테이블에 모든 로그를 쌓으면 실시간 랭킹 조회 시 성능 저하가 발생한다.
* **해결 전략:** 목적에 따른 테이블 이원화.
1. **`RaidRecord`:** `(User + Boss)`를 복합키로 하는 유니크한 성적표. `Atomic Update`를 통해 실시간 누적 데미지와 랭킹을 관리한다.
2. **`RaidHistory`:** 수정 없이 `INSERT`만 발생하는 이력 테이블. 주간/월간 통계 쿼리나 어뷰징 분석에 활용한다.



### 📌 '죽지 않는 보스'와 데이터의 가치

* **도메인 단순화:** `ALIVE`, `DEAD` 같은 복잡한 상태 관리를 없애고, 보스를 **'영구적인 환경 오염 지표'**로 재정의했다.
* **의의:** 보스의 체력이 0이 되어 사라지는 것이 아니라, 누적 데미지(`totalDamage`)가 무한히 증가하는 구조를 통해 "우리 서비스가 이만큼의 쓰레기를 치웠다"는 사회적 가치를 시각화하는 데이터로 승화시켰다.

---

> **오늘의 교훈:** 기술적 화려함(Socket, Real-time)보다는 **'확실한 결과(정산)'**가 사용자에게 더 큰 신뢰를 준다. 또한, 데이터베이스 설계에서 가장 중요한 것은 **'데이터의 생명주기(Lifecycle)'**를 이해하고 분리하는 것이다.
