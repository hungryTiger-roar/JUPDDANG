## 3. 동시성 제어의 딜레마: Dirty Checking vs Atomic Update

쓰레기통 인증 로직을 구현하던 중, 100명의 유저가 동시에 인증을 시도했을 때 카운트가 유실되는 **'갱신 손실'** 문제를 직면했다.

### 📌 JPA의 배신과 JPQL의 구원

* **문제 인식:** JPA의 변경 감지는 `SELECT` -> `Application Memory 수정` -> `UPDATE` 순서로 동작한다. 동시성 환경에서는 여러 스레드가 동일한 초기값(0)을 읽어와서 각자 1로 업데이트해버리기 때문에, 100명이 눌러도 결과는 1이 되는 참사가 발생했다.
* **해결책:** 애플리케이션 레벨의 제어를 포기하고, **DB 레벨의 원자적 연산**을 적용했다.
1. **JPQL 적용:** `UPDATE Trashcan t SET t.count = t.count + 1 WHERE t.id = :id` 쿼리를 통해 DB가 직접 락을 걸고 순차 처리하도록 위임.
2. **영속성 컨텍스트 동기화:** `@Modifying(clearAutomatically = true)` 옵션을 사용하여, DB에 직접 가해진 수정 사항을 무시하고 과거 데이터를 들고 있는 1차 캐시를 강제로 비웠다.


* **깨달음:** CAS나 낙관적 락(`@Version`)은 충돌 시 재시도 로직이 필요해 트래픽 낭비가 심하다. 단순 카운팅 같은 로직은 **'묻지도 따지지도 말고 증가'**시키는 Atomic Query가 가장 효율적이다.

## 4. 테스트의 리얼리티: "성공"보다 중요한 "시나리오"

단순히 "기능이 돌아가는가?"를 넘어, "현실 세계의 물리적 한계를 테스트 코드가 반영하고 있는가?"에 집중했다. 특히 Spring Boot 3.2+ 버전을 도입하며 발생한 환경적 이슈들도 함께 해결했다.

### 📌 Mocking의 정교함과 Spring Boot 3.2 이슈

* **문제 1 (Parameter Name):** Spring Boot 3.2부터 컴파일러가 파라미터 이름을 최적화(삭제)하여 `IllegalArgumentException`이 발생했다.
* -> **해결:** `@RequestParam(name="...")`을 명시하여 컴파일러 옵션에 의존하지 않는 견고한 코드로 수정.


* **문제 2 (NPE in Security):** 테스트 환경에서 `Principal`을 단순히 String(userId)으로 설정했더니, 컨트롤러의 `@AuthenticationPrincipal Account`가 `null`을 반환했다.
* -> **해결:** Mocking 시 실제 DB에서 조회한 `Account` 객체를 주입하여, 실제 런타임과 동일한 인증 컨텍스트를 구성.



### 📌 Happy Path를 넘어선 '경쟁 상태' 검증

* **기존 테스트의 한계:** "100명이 누르면 100명이 성공한다"는 비즈니스 로직(선착순 3명 마감)과 맞지 않는 거짓 테스트였다.
* **시나리오 고도화:**
1. **단일 타겟 경쟁:** 100명이 하나의 쓰레기통에 몰릴 때, **'선착순 3명 성공 + 나머지 97명 거절(400 Error)'**이 발생하는지 검증.
2. **멀티 리전 분산:** 전국 10개 지역에서 동시다발적으로 인증이 일어날 때, 서로 간섭 없이 독립적으로 상태가 변경(`VERIFIED`)되는지 확인.


* **효과:** 단순히 에러가 안 나는 것을 넘어, **'의도한 대로 에러가 나는지'**까지 검증함으로써 시스템의 신뢰도를 확보했다.

---

> **오늘의 교훈:** 동시성 문제에서 가장 강력한 무기는 복잡한 코드보다 **'정확한 SQL 한 줄'**일 때가 많다. 또한, 좋은 테스트 코드는 모든 요청을 성공시키는 것이 아니라, **'현실의 제약(선착순, 마감)'을 정확하게 시뮬레이션**하는 것이다.
