## 비동기의 힘, 메시지 큐 (Message Queue)

### 1. 메시지 큐의 본질
- **메시지(Message):** AP(Application)에서 다른 AP가 이용할 수 있도록 생성하는 데이터 패킷.
- **기원:** 메시지 큐의 원조는 운영체제(OS) 내부 통신.
- **본연의 기능:**
  - 그릇이 물건을 분리 보관하듯, **AP 간의 메시지를 분리하여 비동기적으로 전달**하는 공간 제공.

### 2. 동기 vs 비동기 (음식점 비유)



| 구분 | **동기 (Synchronous)** | **비동기 (Asynchronous)** |
| :--- | :--- | :--- |
| **방식** | 요리사에게 직접 주문 | 주문 박스(큐)를 통한 전달 |
| **특징** | 요리사가 바쁘면 주문 불가 | 요리사가 이해할 수 있는 메시지로 변환하여 전달 |
| **확장성** | 주문량 폭증 시 대처 어려움 | 주문량에 비례해 요리사(Consumer) 고용 가능 |
| **효율성** | - | 조리 가능한 상태의 요리사에게만 메시지 할당 |

### 3. 메시지 경량화의 필요성
- **HTTP의 한계:** 작은 메시지임에도 헤더 등 상당량의 텍스트 크기 차지 (**과대 포장**).
- **최적화:** 메시징을 위한 전용 경량화 프로토콜을 사용하여 최소한의 정보만 전달해야 함.

## 실전 사례: 무인 주차 정산 시스템

### 🚫 동기 방식의 문제점 (Bad Case)
- **문제:** 단순 동기 방식은 외부 REST API(장애우, 유공자 확인 등) 호출 시 하나라도 지연되면 **전체 서비스가 마비**됨.
- **위험:** 요건 분석 실패 시 엄청난 피해가 발생하며, WAS 내부 비동기 처리도 불안정할 수 있어 지양해야 함.

### ✅ 메시지 큐를 활용한 비동기 방식 (Good Case)
- **구조:** 입차 기록만 생성하고, 할인 여부 확인 요청은 **메시지 큐**에 던짐(Publish).
- **처리:** 별도의 **할인 정책 검증 JOB 서버**가 큐에서 메시지를 꺼내(Subscribe) 비동기로 처리.
- **장점:**
  - **성능:** 빠른 응답 속도 보장.
  - **안정성:** 외부 API 장애 시에도 입차 기능은 정상 동작 (Retry 가능).
  - **확장성:** 주문량(입차량) 폭증 시 컨슈머(요리사)만 늘리면 됨.
  - **느슨한 결합:** 큐를 활용하여 인스턴스를 분리, 의존성 최소화.

## MSA와 RabbitMQ

### MSA(Microservices Architecture)에서의 활용
서비스 간의 강한 결합을 끊고, **느슨한 결합(Loose Coupling)**을 위해 메시지 큐가 필수적임.

### RabbitMQ 특징
- **경량화:** 메시지 큐 본연의 기능에 충실.
- **Exchange 라우팅:** 메시지를 목적에 맞게 효율적으로 분기.
- **신뢰성:** 데이터 유실 방지(Durability)에 진심.
- **호환성:** AMQP, MQTT, STOMP 등 다양한 프로토콜 및 언어(Java, Python, Go 등) 지원.

## MQ in SSAFY (프로젝트 적용 가이드)

### 시나리오: 이미지 AI 분류기
1. **문제:** 사용자가 이미지 수십 장 업로드 ➡️ 서버 저장 ➡️ AI 분석 대기 ➡️ 응답. (사용자 무한 대기)
2. **해결:** 이미지를 받자마자 **"접수 완료"** 응답 ➡️ 백그라운드에서 **MQ**를 통해 AI 모델이 순차 처리 ➡️ 완료 시 알림.
3. **효과:** 빠른 응답과 확장성 제공.

### 모든 시작은 '요건 분석' 부터
- **기능 요건:** 지적 재산권이 부여된 다수의 소스 코드를 벡터 임베딩하여 벡터 DB에 저장.
- **비기능 요건:** 대용량 데이터의 분산/병렬 처리 필요 ➡️ **MQ 도입 결정**.

### Conclusion
- **단순하고 낮은 수준의 요건:** 자체 비동기 처리 로직 고려.
- **높은 수준의 신뢰도/대용량 필요:** 적절한 메시지 큐(RabbitMQ, Kafka 등) 도입 필수.
