## 1. ERD 설계

기능 명세를 바탕으로 ERD를 그리다 보면, 정규화의 원칙과 실제 쿼리 성능 사이에서 끊임없이 고민하게 된다. 오늘은 특히 관계 설정과 데이터 타입 결정에 집중했다.

### 📌 논리적 설계와 물리적 구현의 괴리 줄이기

* **관계의 방향성:** 단순히 `1:N`, `N:M` 관계를 긋는 것에 그치지 않고, 실제 비즈니스 로직에서 **'누가 누구를 조회하는 빈도가 높은가'**를 고려해야 한다. 양방향 참조가 꼭 필요한지, 단방향으로 충분한지 판단하여 불필요한 연관 관계를 줄이는 것이 핵심이다.
* **데이터 타입의 선정:** `VARCHAR`의 길이를 단순히 넉넉하게 잡기보다, 인덱싱 효율과 저장 공간을 고려하여 최적의 크기를 선정해야 한다. 특히 날짜 데이터(`TIMESTAMP` vs `DATETIME`)나 좌표 값 등 특수 타입은 추후 확장을 고려해 신중히 결정한다.

### 📌 확장성을 고려한 식별자 전략

* **PK 전략:** 비즈니스 의미가 담긴 자연키보다는, 유연성을 위해 대리키를 사용하는 것이 추후 키 변경이나 데이터 마이그레이션 상황에서 유리하다는 점을 다시금 상기했다.

## 2. 기능 명세와 구현 가능성: '상상'을 '현실'로 만드는 필터링

기획 단계에서 정의된 기능이 개발 단계에서 기술적 부채가 되지 않으려면, 명세 작성 시점부터 개발자의 시각으로 '구현 가능성'을 검증해야 한다.

### 📌 Happy Path가 아닌 Edge Case에 집중하기

* **예외 상황 시나리오:** "사용자가 버튼을 누르면 저장된다"는 명세는 불충분하다. "네트워크가 끊겼을 때는?", "동시 접속자가 몰려 DB 락이 걸렸을 때는?"과 같은 **Edge Case**를 명세서에 포함시켜야 방어적인 코드를 짤 수 있다.
* **트랜잭션 범위 설정:** 기능 하나가 너무 많은 테이블을 동시에 건드리지 않는지 점검한다. 트랜잭션이 길어지면 성능 저하의 원인이 되므로, 기능을 더 작은 단위로 쪼개거나 비동기 처리가 가능한지 검토가 필요하다.

### 📌 외부 의존성과 기술적 제약

* **API 제약 사항:** 외부 API를 사용할 경우, 해당 서비스의 Rate Limit이나 응답 속도가 우리 서비스의 병목이 되지 않도록 캐싱 전략이나 폴백 프로세스를 미리 명세에 녹여내야 한다.

## 3. DB 설계가 곧 비즈니스 로직이다

오늘 명세를 작성하며 느낀 점은, DB 설계가 탄탄해야 비즈니스 로직이 단순해진다는 것이다.

### 📌 상태(Status) 관리의 명확화

* **Enum 활용:** 주문 상태나 유저 상태 등을 단순 문자열이 아닌 명확한 `Enum` 혹은 `Code Table`로 정의하여, 코드 레벨에서의 분기 처리를 줄이고 데이터의 일관성을 보장해야 한다.
* **Default Value:** 컬럼의 `Default Value`와 `Not Null` 제약 조건을 적극적으로 활용하여, 애플리케이션단에서 발생할 수 있는 `NullPointException` 가능성을 DB 레벨에서 1차적으로 차단한다.

> **오늘의 교훈:** ERD와 기능 명세서는 개발을 위한 지도다. 지도가 부정확하면 목적지에 도달하는 비용이 배로 든다. 코드를 치기 전, **설계도 위에서 시뮬레이션을 충분히 돌려보는 것**이 가장 빠른 지름길이다.
