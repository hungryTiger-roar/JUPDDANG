## 1. 개발 환경 구축과 아키텍처 의사결정

본격적인 기능 개발에 앞서, 모니터링 및 배포 환경을 세팅하며 **'컨테이너의 격리성'**과 **'네트워크의 복잡성'** 사이에서 최적의 구조를 고민했다. 오늘은 무조건적인 Docker 도입보다는 상황에 맞는 유연한 아키텍처 선정에 집중했다.

### 📌 Docker Native vs Host Native

* **Reverse Proxy의 위치 선정:** 초기에는 Nginx와 Grafana 모두를 Docker 컨테이너로 띄우려 했으나, Host의 포트 점유 문제와 네트워크 라우팅 충돌이 발생했다.
* **결정:** 애플리케이션(Grafana)은 의존성 관리가 중요한 **Docker**로, 외부 요청을 가장 먼저 받아야 하는 진입점은 **Host Native**로 분리했다. 이를 통해 `Docker Network`의 복잡성을 줄이고, 디버깅 용이성을 확보했다.

### 📌 인프라 설정도 '코드'다

* **Config 관리:** Nginx의 `conf.d`와 `sites-available` 설정 파일, 그리고 `docker-compose.yml`은 단순한 텍스트 파일이 아니라 서버의 동작을 결정하는 핵심 코드다.
* **교훈:** 설정 파일의 오타 하나(URL 불일치), 경로 설정 실수 하나가 전체 서비스의 `502 Bad Gateway`를 유발한다. 인프라 설정 변경 시에도 코드 리뷰에 준하는 검증 과정(`nginx -t`, `dry-run`)이 필수적임을 깨달았다.

## 2. 트러블 슈팅: '연결'을 가로막는 보이지 않는 벽

서버를 세팅하며 겪은 `Connection Refused`와 `404 Not Found`는 단순한 에러가 아니었다. 이는 클라이언트에서 서버 내부까지 도달하는 **Packet Flow**를 이해하는 과정이었다.

### 📌 다중 방화벽 구조의 이해

* **이중 잠금 장치:** 단순히 OS 레벨의 방화벽(`UFW`)만 열었다고 끝난 것이 아니다. 클라우드 환경에서는 **Security Group(외부 방화벽)**이라는 또 하나의 대문이 존재한다.
* **해결:** `UFW allow 80/443` 명령어와 함께 클라우드 콘솔의 **Inbound Rules**를 동시에 점검해야 한다. 연결이 거부될 때는 내부(`curl localhost`)와 외부(`curl domain`) 테스트를 분리하여 문제의 레이어를 좁혀나가는 방식이 유효했다.

### 📌 '캐시'와 '오타'라는 함정

* **브라우저의 거짓말:** 브라우저는 사용자 경험을 위해 리다이렉트 정보나 에러 페이지를 캐싱한다. 인프라 설정 변경 직후에는 반드시 **시크릿 모드**나 `curl` 명령어를 통해 **Raw Data**를 확인해야 잘못된 디버깅을 피할 수 있다.
* **정확한 타겟팅:** 작업 중인 서버(`D208`)와 테스트 중인 URL(`A208`)이 일치하는지 확인하는 것은 기본 중의 기본이다. 사소한 철자 확인이 몇 시간의 삽질을 줄여준다.

## 3. 보안은 선택이 아닌 필수 조건

기능 구현 전 SSL을 먼저 도입한 이유는, 보안이 나중에 덧붙이는 '기능'이 아니라 서비스가 구동되는 '기반 환경'이기 때문이다.

### 📌 SSL/HTTPS 도입과 Certbot

* **데이터의 밀봉:** HTTP는 중간에 누구나 내용을 볼 수 있다. 로그인 기능이 포함된 Grafana를 운영하기 위해서는 데이터 암호화가 필수적이다.
* **자동화 도구 활용:** `Certbot`을 통해 Let's Encrypt 인증서를 발급받고, Nginx의 443 리다이렉트 설정을 자동화했다. 이를 통해 '보안 경고' 없는 신뢰할 수 있는 모니터링 환경을 구축했다.

> **오늘의 교훈:** 로그(`access.log`, `error.log`)와 상태 코드(`302`, `200`, `502`)를 근거로 논리적으로 추론하는 것이 인프라 트러블 슈팅의 지름길이다.
