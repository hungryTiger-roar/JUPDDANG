### 1. 환경 설정의 구체화와 로그 가시성 확보

애플리케이션이 구동되는 토대를 다지는 과정에서, 코드와 설정을 분리하고 로그의 가독성을 높이는 작업의 중요성을 체감했다. 단순한 '실행'을 넘어 '운영 가능한' 상태를 만드는 데 집중했다.

**📌 `env` 설정과 `properties`의 유기적 연동**

* **설정과 코드의 분리:** 민감한 정보나 환경별로 달라지는 값들을 하드코딩하지 않고 시스템 환경 변수(`env`)로 빼낸 뒤, 이를 애플리케이션의 `properties` 파일과 매핑했다.
* **결정:** 보안이 필요한 DB 접속 정보나 API 키 등은 `env`로 관리하여 유연성을 확보하고, 소스 코드 저장소에는 껍데기만 올라가도록 구조를 잡았다. 이를 통해 배포 환경이 바뀌어도 코드 수정 없이 설정 변경만으로 대응 가능한 구조를 마련했다.

**📌 깨진 문자의 역습: 로그 인코딩 트러블 슈팅**

* **문제 상황:** 서버 로그를 확인하던 중 한글 메시지가 깨져서 출력되는 현상(???? 혹은 외계어)을 발견했다. 로그는 시스템의 블랙박스인데, 내용을 읽을 수 없다면 무용지물이다.
* **해결 및 교훈:** 단순한 폰트 문제가 아닌 JVM 혹은 OS 레벨의 인코딩 불일치 문제였다. 서버의 로케일 설정과 실행 옵션(Dfile.encoding=UTF-8 등)을 일치시켜 한글 로그를 복구했다. 개발 환경뿐만 아니라 운영 서버의 인코딩 셋까지 챙겨야 진정한 '완료'임을 깨달았다.

### 2. 자동화의 첫걸음: GitLab CI/CD 도입

매번 수동으로 빌드하고 배포하던 과정을 자동화하기 위해 GitLab CI/CD 파이프라인을 처음으로 구축했다. 내 로컬이 아닌 'Runner'가 대신 일하게 만드는 과정은 생각보다 정교한 설정이 필요했다.

**📌 GitLab Runner와 서버의 핸드쉐이크**

* **Runner의 역할:** GitLab의 파이프라인 스크립트를 실제로 수행할 Runner을 서버에 직접 설치하고 등록Register했다.
* **트러블 슈팅:** 단순히 설치만 한다고 끝나는 것이 아니라, Runner가 사용할 Executor, shell, docker 등를 지정하고 권한을 부여하는 과정이 필요했다. 서버가 곧 배포 환경이자 빌드 환경이 되므로, Runner가 서버의 자원에 접근할 수 있도록 경로와 권한 설정을 꼼꼼히 챙겨야 했다.

**📌 CI/CD가 가져다준 변화**

* **수동에서 자동으료:** 이제 코드를 푸시하는 행위 자체가 배포의 시작이 되었다.
* **교훈:** 처음 러너를 설정할 때는 복잡해 보였지만, 한 번 구축해두니 반복적인 빌드/배포 명령어를 칠 필요가 없어졌다. 인프라 설정은 초기에 공수가 들더라도 장기적인 생산성을 위해 반드시 투자해야 하는 영역임을 확인했다.
